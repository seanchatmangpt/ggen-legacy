# After Code Reading — Control Architecture

## 0. Claim boundary

This document is the target control-architecture projection of `product/AFTER_CODE_READING.md` and part of the bounded After Code Reading strategic corpus. The corpus may receive `ALIVE / REFERENCE_CONFORMANT` only when its dedicated exact-head workflow independently re-derives this plane model, executes two clean documentary replays, rejects sabotage controls, and binds the result into a receipt.

That standing proves the architecture corpus is internally admitted, reproducible, and independently verifiable. It does not assert that every runtime plane already executes, that a complete replacement has passed the no-read admission theorem, or that the architecture is production-proven. Runtime implementation standing remains governed by `RELEASE_CONTROL.md` and the Claims Register.

## 1. Architectural objective

Remove mandatory human implementation reading from the production critical path without weakening accountability.

The architecture must replace source inspection with a closed control system over:

- authoritative requirements;
- architecture and policy;
- deterministic and probabilistic planning;
- bounded manufacture;
- separated actuation authority;
- independent falsification;
- runtime evidence;
- explicit standing;
- receipts and replay;
- standard revision.

## 3. Plane model

### Mission Plane

Humans define business consequences, architecture, invariants, risk boundaries, acceptance, and irreversible decisions.

The Mission Plane must not express implementation detail merely to compensate for weak downstream authority. It defines what must be true, what must never become true, and what evidence is required.

### Observation Plane

Observers inspect repositories, history, binaries, interfaces, tests, configuration, deployments, workflows, events, and downstream consumers.

Observations remain partial until admitted. Zero findings and unexecuted observation remain different states.

### Admission Plane

Schemas, SHACL, policy, provenance, source identity, contradiction checks, and disclosure rules transform bounded observations into authority.

The Admission Plane owns the distinction:

```text
observed ≠ inferred ≠ admitted ≠ refused ≠ unknown
```

### Architecture Plane

Machine-readable architecture defines:

- component boundaries;
- dependency direction;
- data contracts;
- trust zones;
- allowed technologies;
- performance budgets;
- security and privacy obligations;
- output ownership;
- generated-surface ownership;
- retirement constraints.

This plane replaces architectural drift detection that would otherwise depend on human source reading.

### Planning Plane

Deterministic PDDL, probabilistic PPDDL, workflow planning, and allocation select lawful production routes.

The Planning Plane must represent:

- no-change as a successful result;
- abstention;
- typed refusal;
- stochastic outcomes;
- observation actions;
- bounded repair;
- risk constraints;
- resource limits;
- required verification and receipts.

Planning produces candidates or intents. It does not receive implicit authority to actuate.

### Manufacturing Plane

Projectors, templates, compilers, agents, and production cells manufacture:

- application and service code;
- infrastructure and deployment surfaces;
- tests and fixtures;
- schemas and policies;
- APIs and integration adapters;
- observability;
- evidence projections;
- documentation.

Generated implementation is work in process until independent verification establishes standing.

### Actuation Plane

A broker receives explicit, bounded authorization and performs filesystem, process, network, deployment, migration, publication, and external API mutations.

The hard invariant is:

```text
selection ≠ authorization ≠ execution
```

The planner, manufacturer, and verifier receive no ambient production authority.

### Inspection Plane

Mechanical inspection includes:

- compilation and type checking;
- static and dependency analysis;
- architecture conformance;
- unit, property, integration, contract, and black-box tests;
- fuzzing and mutation testing;
- security and privacy controls;
- performance, stress, chaos, and resilience tests;
- generated-output drift detection.

Inspection is not sufficient when the same producer defines, executes, and interprets every check.

### Independent Verification Plane

Independent verifiers rederive material claims from admitted authority and observed artifacts.

They must be capable of producing counterexamples and typed refusal. They do not trust generated reports merely because those reports are internally consistent.

### Process Evidence Plane

Runtime evidence records what actually moved:

- event sequence;
- object identity;
- actor and authority;
- inputs and outputs;
- side effects;
- failures and retries;
- policy decisions;
- conformance deviations;
- terminal consequences.

The source describes what was manufactured. Process evidence establishes what executed.

### Standing Plane

A crown verifier assigns one of the canonical states:

- `PARTIAL_ALIVE`
- `ALIVE`
- `BLOCKED`
- `BUILD_BROKEN`
- `UNKNOWN`
- `UNSUPPORTED`

A report may project standing but cannot create it independently.

### Receipt and Replay Plane

Receipts bind exact source, authority, toolchain, plan, authorization, execution, verifier results, evidence, and lineage.

Replay re-executes from clean state and requires declared equivalence such as:

```text
NO_SEMANTIC_CHANGE
NO_GENERATED_DRIFT
REPLAY_MATCH
```

### Improvement Plane

Observed abnormalities become typed improvement work:

```text
abnormality
→ stop
→ root cause
→ countermeasure
→ standard revision
→ new manufacture
→ new receipt
```

The implementation is not patched manually to create apparent conformance. Authority, template, projector, planner, verifier, or admission law is repaired at the earliest lawful cause.

## 6. Human interaction model

The human interface must project objects above implementation:

- requirement and architecture graphs;
- planner alternatives and risk tradeoffs;
- authorization requests;
- counterexamples;

Source code may remain available as an evidence surface, but it is not the mandatory governing interface.

A product claiming After Code Reading must implement or explicitly mark `UNKNOWN` for:

4. planning and abstention;

No missing control may be replaced with editorial confidence.

## 9. No-read admission theorem

A bounded capability may claim that manual source reading was removed only when:

```text
requirements_admitted=true
architecture_constraints_executable=true
planning_closed=true
actuation_brokered=true
producer_verifier_separated=true
positive_witnesses_passed=true
negative_falsifiers_passed=true
operational_evidence_bound=true
receipt_valid=true
replay_match=true
manual_implementation_reading_required=false
standing=ALIVE
```

The theorem is bounded to the declared capability and exact source identity. It cannot be generalized to the whole repository or organization without a crown verifier over that broader object.

## 10. Same-object falsifier

The architecture fails its stated objective when acceptance requires human source inspection because any required semantic, architectural, behavioral, operational, or evidentiary distinction is unavailable elsewhere.

The architecture also fails when a no-read result depends on one producer's own tests, reports, or confidence without independent rederivation.

## 12. Architecture nonclaims

This architecture does not claim:

- unrestricted program equivalence;
- universal support for every language or runtime;
- zero human judgment;
- zero residual risk;
- tests alone establish correctness;
- current implementation of every plane;
- external production proof;
- automatic predecessor retirement.
