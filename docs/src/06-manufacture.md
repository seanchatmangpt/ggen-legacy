# Repository Manufacture

## Category

Verified Repository Reconstitution reconstructs a repository’s real observable contract, admits it as machine-readable authority, manufactures a replacement, independently verifies closure, replays the result, and computes whether the predecessor may retire.

This is materially stronger than rewrite, migration, modernization, refactoring, or code generation. Those may participate, but none alone establishes repository standing.

## Repository archaeology

The declared observation surface includes Git history, deleted paths, commands and aliases, defaults, configuration, diagnostics, public APIs, generated files, templates, tests, workflows, packaging, migration commits, runtime traces, and downstream contracts.

Each observer reports scope, exact coordinate, findings, exclusions, errors, and standing. An unexecuted observer remains `UNKNOWN`; a completed zero-result search is an observed zero.

## Semantic admission

Observations become authority only after provenance, schema, SHACL, policy, and contradiction checks. Use public vocabularies first: PROV-O, DCAT, DCTERMS, SKOS, SHACL, ODRL, OCEL, QUDT, and SOSA where applicable.

The ontology is the source of possible lawful consequences. One admitted fact may drive description, constraints, generation, validation, planning, operation, observability, repair, explanation, attestation, replay, and documentation. Every consequence must be semantically entailed, bounded, validated, owned, and receiptable.

## Capability ledger

A LegacyCapability records identity, provenance, historical owner, observable contract, current owner, disposition, equivalence case, verifier, receipt, and standing.

Final dispositions are:

- `PRESERVED`
- `SUBSUMED`
- `REPLACED`
- `ARCHIVED`
- `REFUSED`

`UNKNOWN` may exist during investigation but must be zero at final admission. Refusal requires a negative contract and falsifier. Archival requires evidence that behavior is excluded from active operation while retained for history or forensics.

## Design for Combinatorial Maximalism

Combinatorial maximalism maximizes reversible graph-domain construction before machine-state actuation. Internal implementation variation is represented as bounded candidate lattices rather than scattered conditionals.

Dimensions may include runtime, storage, protocol, serialization, consistency, deployment, generation cardinality, ownership, recovery, and verification.

The system:

1. generates candidate combinations reversibly;
2. bounds coverage by declared cardinality and resource policy;
3. admits only candidates passing fail-closed gates;
4. routes mutation through one atomic broker;
5. receipts exact inputs and outputs;
6. repeats synchronization for byte identity;
7. sabotages authority, ownership, closure, ordering, actuation, and replay with negative fixtures.

A large generated set without gates is uncontrolled expansion, not maximalism.

## Building Blocks and packs

One canonical GBB kernel owns architecture truth. Domain profiles compose it; they do not fork it.

A pack is an executable distribution theorem: one admitted semantic state projected across bounded verified artifacts. An external pack carries identity, version, compatibility law, bounded write authority, dependency disclosure, consumer capabilities, conformance evidence, portable receipts, lawful substitution, and host-independent documentation.

## Behavioral equivalence

Equivalence is declared observable-contract equivalence, not unrestricted program equivalence. Cases may compare exit codes, stdout/stderr, generated bytes, filesystem consequences, diagnostics, events, API behavior, receipt topology, side effects, recovery, and refusal behavior.

The same objects and operation coordinate must be compared. Adjacent demonstrations do not close a missing behavior.
