# After Code Reading — Product and Category Doctrine

## 0. Claim boundary

This document is part of the bounded `ggen-legacy v26.8.1` After Code Reading strategic corpus. That corpus may receive `ALIVE / REFERENCE_CONFORMANT` only through the dedicated exact-head workflow that executes non-promoting manufacture, two clean documentary replays, producer-verifier separation, negative controls, receipt binding, and an independent read-only crown.

The promotion is bounded to the doctrine, authority, architecture, review standard, and documentation projections. It does not claim that the complete software-manufacturing method already executes, that a real legacy replacement has been admitted without source reading, that human source reading is universally obsolete, that tests alone prove correctness, or that any external person endorses this repository. Complete product implementation and external production standing remain governed by `RELEASE_CONTROL.md` and the Claims Register.

## 1. Historical hinge

On 2026-07-23, Robert C. Martin publicly described a workflow in which he does not read agent-written implementation because mandatory human reading would prevent him from realizing the agents' productivity. He described replacing implementation inspection with an extensive gauntlet of unit tests, executable scenarios, QA procedures, quality metrics, mutation testing, coverage, and related constraints.

Primary public coordinate:

`https://x.com/unclebobmartin/status/2080257779395154409`

That event does not prove the doctrine in this document. It makes a long-form engineering boundary publicly legible:

> Machine implementation throughput can exceed human source-inspection throughput. When mandatory line-by-line review remains the governing gate, human reading becomes the factory bottleneck.

## 3. Category stack

### After Manual Code

The broad historical transition from software production governed by manual implementation construction to machine-scale manufacture.

### After Code Reading

The engineering boundary at which mandatory human source inspection leaves the production critical path and is replaced by stronger admitted controls and evidence.

### Proof-Carrying Software Manufacturing

The method that manufactures software through admitted requirements, planning, bounded authority, independent falsification, operational evidence, typed standing, receipts, and replay.

### Software Systems Manufacturer

The accountable profession after manual code construction and inspection leave the critical path. The manufacturer governs mission, architecture, boundaries, risk, standards, acceptance, verifier design, evidence interpretation, exceptions, and irreversible decisions.

### Verified Repository Reconstitution

The `ggen-legacy` product category within this movement. It reconstructs a predecessor's observable contract, admits that contract as authority, manufactures a replacement, independently verifies closure, replays the result, and computes Release Admission and Sunset Admission separately.

The stable relationship is:

> **After Manual Code is the transition. After Code Reading is the boundary. Proof-Carrying Software Manufacturing is the method. Software Systems Manufacturer is the profession. Verified Repository Reconstitution is the ggen-legacy product contribution.**

## 4. Governing thesis

> The age of software governed primarily by humans reading and writing implementation is ending. Machine-scale production requires admitted specifications, architecture, full planning, bounded actuation, independent verification, operational evidence, explicit standing, receipts, and replay.

Code is not the product.

Code is intermediate manufacturing material.

The product is a verified business capability or a conforming operational system.

## 5. The old and new production models

### Traditional software production

```text
human requirement
→ human writes implementation
→ another human reads implementation
→ tests run
→ software ships
```

### Mechanized writing with manual inspection

```text
human prompt
→ agent writes implementation at machine speed
→ human reads implementation at human speed
→ tests run
→ software ships
```

This is not a new production system. It accelerates one workstation while preserving the human inspection bottleneck.

### Proof-carrying manufacture

```text
human defines intended consequences
→ requirements and architecture become admitted authority
→ planners select lawful production routes
→ bounded agents manufacture complete capabilities
→ independent mechanisms attempt falsification
→ runtime evidence records actual consequences
→ standing is computed
→ receipts bind the production path
→ replay establishes reproducibility
```

## 6. What replaces source reading

A no-read system is acceptable only when it replaces source inspection with a stronger, explicit assurance system.

### Admission

Inputs are bounded and authoritative:

- business requirements;
- architecture rules;
- security policy;
- data contracts;
- infrastructure constraints;
- accepted dependencies;
- performance budgets;
- regulatory obligations;
- refusal conditions.

Agent inference does not become authority merely because it is plausible.

### Planning

The system selects intended state transitions before implementation is produced. Planning must represent:

- legal actions;
- prohibited actions;
- no-change as a valid outcome;
- abstention and refusal;
- uncertainty;
- recovery;
- risk constraints;
- required evidence.

### Manufacture

Agents and generators may construct:

- applications;
- services;
- integrations;
- infrastructure;
- policy;
- tests;
- deployment surfaces;
- observability;
- operational controls;
- documentation and evidence projections.

### Mechanical inspection

The product may be challenged through:

- compilation and type checking;
- static analysis;
- architecture conformance;
- dependency and license policy;
- unit, property, integration, contract, and black-box tests;
- fuzzing and mutation testing;
- security analysis;
- performance, chaos, resilience, and replay tests.

### Independent falsification

A producer cannot certify itself. Separate mechanisms must attempt to disprove behavioral correctness, architectural conformity, safety, closure, reproducibility, and operational readiness.

### Standing

Accepted states are explicit:

- `PARTIAL_ALIVE`
- `ALIVE`
- `BLOCKED`
- `BUILD_BROKEN`
- `UNKNOWN`
- `UNSUPPORTED`

Confidence language does not replace standing.

### Receipt and replay

A material result binds:

- admitted inputs;
- exact source and authority identity;
- production route;
- toolchain;
- verifier results;
- artifacts and digests;
- failures and refusals;
- approvals;
- predecessor relationships;
- replay result.

The governing question changes from “Who read the code?” to:

> **What did the artifact survive, who authorized its requirements, which independent mechanisms tried to falsify it, and can the complete result be replayed?**

## 7. Human responsibility after code reading

The doctrine does not remove human accountability. It moves human judgment to the larger system boundary.

Humans retain authority over:

- mission and business consequences;
- architecture and invariants;
- risk and security boundaries;
- acceptance criteria;
- verifier design;
- evidence interpretation;
- exception handling;
- irreversible decisions;
- Release and Sunset authorization.

The accountable human need not know every implementation line. The accountable human must know the production law under which every artifact was admitted, generated, inspected, refused, accepted, or retired.

Legacy replacement is the decisive proving ground for After Code Reading because the predecessor contract is rarely available as one clean specification.

`ggen-legacy` must:

1. observe historical and current behavior without equating observation with authority;
2. reconstruct the bounded observable contract;
3. admit that contract through schema, SHACL, provenance, contradiction, and policy checks;
4. assign every capability a final disposition;

## 10. The central challenge to industry

> **Most organizations have accelerated code generation without replacing the human inspection system that governs production. They installed new machinery but preserved the old factory.**

AI-assisted development is therefore insufficient when its governing loop remains:

```text
machine writes
→ human reads
→ human approves
```

A genuinely AI-native organization requires:

```text
human governs consequences
→ machinery manufactures
→ independent machinery falsifies
→ evidence determines standing
```

## 12. Benchmark program

The primary productivity metric is not generated code, commits, or tokens.

```text
Post-Reading Throughput
=
verified engineering consequences
/
(human inspection time + elapsed time + compute + coordination)
```

Required dimensions include:

- verified business consequences;
- manual source lines read and written;
- human attention minutes;
- executable requirements admitted;
- architecture violations detected;
- mutation score;
- property and fuzz failures;
- security findings;
- replay success;
- receipt completeness;
- unsupported claims refused;
- unnecessary actions avoided;
- time from observation to standing;
- cost per verified consequence.

The signature demonstration is:

> **A bounded capability is manufactured, independently verified, receipted, and replayed while the accountable human reads zero implementation lines.**

That statement may be made only when the evidence explicitly measures the human inspection boundary.

## 13. Falsifier

The doctrine is falsified for a declared product boundary when any of the following is observed:

- humans must inspect implementation to decide acceptance because requirements or evidence are insufficient;
- an agent-generated test suite is the only verifier of agent-generated implementation;
- architecture can drift without machine detection;
- successful planning silently becomes actuation authority;
- missing evidence or silence is promoted into success;
- receipts cannot reproduce the production path;
- an artifact receives `ALIVE` without independent replay;
- the system cannot represent no-change, refusal, or unsupported scope as a valid outcome.

## 14. Nonclaims

This doctrine does not assert:

- source reading has no value;
- source reading is prohibited in every risk class;
- automated testing proves unrestricted program correctness;
- all software can be manufactured without human intervention;
- the complete ecosystem is already integrated;
- every repository can receive Sunset Admission;
- the public statement that motivated this pivot endorses this architecture.
